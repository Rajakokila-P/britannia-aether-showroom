SOFTWARE CASE STUDY / PERSONAL PROJECT

Building a fast,
static-first showroom.

One working website brings four fictional automotive designs together through comparison, filtering and downloadable concept briefs. The implementation keeps interactions in the browser and publishes static files through GitHub Pages.

Try the live showroom ↗View the source on GitHub ↗

The problem

Present a visually rich collection without making visitors download oversized imagery or implying that speculative vehicles are available to buy. Let visitors compare concepts and save preferences while keeping the implementation maintainable for a small personal project.

Role and contribution

The project owner supplied the concept direction, imagery and decisions about the showroom experience. Website implementation, performance refinements and verification were carried out with AI coding assistance. This case study documents the delivered software; it does not claim sole authorship, employment experience or production vehicle engineering.

Tech stack

Semantic HTML, responsive CSS, vanilla JavaScript, native browser dialogs, WebP images and Blob-based text downloads. Python validates internal references; Node.js checks JavaScript syntax. GitHub Actions packages the site and deploys it to GitHub Pages.

Architecture

  1. Delivery: GitHub Pages serves HTML, CSS, JavaScript and images. There is no custom application server or database.
  2. Interaction: a model array in app.js drives the collection cards, filters, dialogs and configurator. Event handlers update the DOM and selected edition or cabin mood.
  3. Download: the browser builds a text brief from the current selection, creates a Blob URL and starts a local download. Selections are not sent to a sales service.
  4. Contact: contact.js validates inputs and encodes a mailto draft. The visitor sends it through their own email application; the website does not submit or store the message.
  5. Release: a push to main runs source validation, uploads the site directory as a Pages artifact and deploys only after validation passes.

Implementation decisions

Optimized WebP assets and responsive image variants reduce unnecessary image downloads. The hero is prioritised, below-fold images are lazy-loaded, and system fonts remove external font requests. Native controls, visible focus states and reduced-motion styles support keyboard and motion-sensitive users.

The static approach fits this scope, but has deliberate limits: no cross-device saved configurations, no server-delivered contact messages and no customer accounts. Vehicle settings describe concepts rather than simulated engineering behaviour.

Earlier browser checks verified filtering, dialog dismissal, configuration changes and the generated Nomad brief. Responsive checks found no horizontal document overflow at 390, 768 and 1440 CSS pixels. No user-traffic, revenue, backend-latency or vehicle-performance metrics are claimed.

Lessons learned

Asset delivery mattered more than introducing a framework. Testing the live site complemented local audits, and a high overall score still required inspection of individual findings. Keeping speculative vehicle descriptions separate from measured website behaviour makes the portfolio more credible.
